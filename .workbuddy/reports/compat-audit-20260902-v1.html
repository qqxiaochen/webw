Compatibility Audit · v1

老旧浏览器内核兼容性评估报告

针对 PaoMian Hax 官网（paomfz.com）三份页面与全部第三方依赖，逐项识别 IE11 / EdgeHTML / 旧 WebKit / 旧 Firefox / 旧 Chromium 上不被支持的前端特性，标注受影响的内核版本、运行时症状与降级方案。

评估日期 2026-09-02 扫描范围 index / download / 404 共 1695 行 第三方 JS 库 0 个 问题项 42 条 方法 静态扫描 + 线上实测

总体结论

JavaScript 层面出人意料地干净。三份页面的脚本全部是 ES5 写法——没有 let/const、没有箭头函数、没有模板字符串、没有解构与展开运算、没有 for...of。机器扫描确认 ES6+ 语法命中 0 处。这意味着不需要引入 Babel 或任何构建期转译，这是本次评估最重要的好消息。

真正的重灾区在 CSS，且集中在一个根因上：全站 225 处 var() 引用。IE11 完全不支持 CSS 自定义属性，所有含 var() 的声明会被整条丢弃——深色背景、文字颜色、字体栈、圆角、阴影、玻璃质感会同时消失，页面退化为「白底 + 黑字 + 直角 + 宋体」。内容仍可读、下载链接仍可点，但品牌视觉 100% 丢失。这不是 20 个独立问题，而是一个根因引发的连锁崩塌，因此修复成本远看上去低。

有一处设计陷阱值得单独点名：index.html:277-282 用 @supports not (aspect-ratio) 写降级。这个写法在 IE11 上等于没有降级——因为 IE11 连 @supports 本身都不支持，整个兜底块会被直接丢弃，导致 YouTube 视频容器高度塌陷为 0。用 @supports 写的兜底，救不了不支持 @supports 的浏览器。方向应该反过来：默认用 padding hack，再用 @supports 升级到 aspect-ratio。

但请先读完第 6 节再决定投入。本站用户是越南/菲律宾/欧美的 CF 玩家，IE11 实际占比大概率低于 0.1%，而东南亚老旧 Android WebView（UC / QQ / X5 内核）可能占 5–15%。「老旧内核」这个词在你们的用户群里，指的恐怕不是 IE。建议先去 Cloudflare 面板导出 UA 分布再排优先级——站点目前没有任何统计埋点，谁都说不准真实占比。

为什么本次没有 P0

P0 定义为「核心转化路径不可用或页面不可读」。扫描下来最坏的情况是 IE11：视觉体系崩塌、部分交互失效，但三份页面的 HTML 内容、下载链接、购买入口全部可达且可读。因此最高只到 P1。需要注意——pay.paomfz.com 持续返回 403、mall.909net.cn 不可达，这两个是既往已记录的 P0，但它们与浏览器兼容性无关，属于运维问题，本报告仅在 DEP-04 顺带复核状态。

// 1) 滚动位置：IE 全系无 scrollY
function scrollTop(){
  return window.pageYOffset != null
    ? window.pageYOffset
    : (document.documentElement.scrollTop || document.body.scrollTop || 0);
}
// 替换 4 处 window.scrollY → scrollTop()

// 2) closest polyfill（MDN 标准写法，覆盖 IE9+ / 旧 WebKit）
if (window.Element && !Element.prototype.closest) {
  Element.prototype.matches = Element.prototype.matches
    || Element.prototype.msMatchesSelector
    || Element.prototype.webkitMatchesSelector;
  Element.prototype.closest = function(s){
    var el = this;
    do { if (el.matches && el.matches(s)) return el; el = el.parentElement; }
    while (el !== null);
    return null;
  };
}

// 3) classList.toggle 第二参：改用显式 add/remove，避免 IE 闪烁

+ var sc = scrollTop() > 24;
+ if (sc) { nav.classList.add('scrolled'); } else { nav.classList.remove('scrolled'); }

- if (e.key === 'Escape' && modal.classList.contains('open')) closeModal();

CSS-01 的修复成本被高估了

225 处 var() 看着吓人，但不需要逐处改。两种低成本做法任选：
① 静态回退值——在影响可读性的关键声明前补一行静态值（CSS 解析规则天然支持，新浏览器用后者覆盖）：约 20 处，IE11 立即得到「深色实底 + 白字 + 直角」的可读页面。
② IE 专属兜底块——用 @media all and (-ms-high-contrast:none), (-ms-high-contrast:active){ :root{...实色覆盖...} }（IE10/11 专属 hack），一处覆盖全部 token，改动量最小且不动主样式。

6 · 逐浏览器降级矩阵

"可用度"＝内容可读性 + 核心转化路径（下载 / 购买）可达性 + 视觉保真度的综合判断。

浏览器 / 内核可用度核心症状（按影响排序）
IE11
Trident 7.0		 35% ① var() 全废 → 白底黑字直角宋体，玻璃质感归零（CSS-01）；② 视频区高度塌陷为 0（CSS-02）；③ 整卡下载点击抛错失效（JS-03）；④ 返回顶部按钮永不出现（JS-02）；⑤ 导航条滚动时高频闪烁（JS-04）；⑥ Esc 关窗失效（JS-05）；⑦ flex gap 全丢，元素挤在一起（CSS-06）；⑧ grid → 单列堆叠（CSS-05）；⑨ YouTube 提示不支持（DEP-03）；⑩ 若落入兼容性视图则近乎全崩（HTML-01）。内容可读、下载链接可点，但视觉与交互严重受损。

请优先关注矩阵的后两行，而不是第一行

本站用户是越南 / 菲律宾 / 欧美的 CrossFire 玩家。这个群体的设备画像决定了：IE11 的实际占比大概率低于 0.1%，而东南亚中低端 Android 机上的 UC / QQ / X5 内核可能占到 5–15%。换句话说，为 IE11 投入两周改造，可能覆盖不到千分之一的用户；而把 Chrome 49 以下内核的 var() 崩塌修掉，覆盖的可能是十分之一。
所以修复顺序建议是：先修「跨内核通杀」的根因项（CSS-01 的 var 兜底、JS-03 的 closest、JS-02 的 scrollY、CSS-02 的 aspect-ratio 方向），这些改动同时惠及 IE11、EdgeHTML、旧 X5 内核，一份投入三处收益；再评估是否为 IE11 单独补 gap / grid / filter。
但 DEP-07 说得很清楚：站点没有任何统计埋点，以上全是推断。动手前请先去 Cloudflare 面板导出一份 UA 分布——这一步只要 5 分钟，能让后面所有决策从"猜"变成"算"。

7 · 修复与降级方案

四个方案，按推荐度排序。A 是主菜，D 是无论如何都该做的保底。

推荐 方案 A · 渐进增强改写（零构建，纯手工） 约 2 小时 · 覆盖 6 条 P1 中的 5 条

核心思路：把「现代特性 + 兜底补丁」的写法，统一改成「基础写法 + 现代特性升级」。前者在不认识兜底语法的浏览器上等于没兜底，后者天然安全。

  1. HTML-01：给 index / download 补 X-UA-Compatible（2 行，5 分钟）。必须最先做，否则 IE 落入兼容性视图会让后续所有修复失效。
  2. CSS-01：加 IE10/11 专属 @media -ms-high-contrast 兜底块，把关键 token 覆盖为实色；再给 body / .glass / .btn-primary 等约 20 处关键声明补静态回退值。
  3. CSS-02：aspect-ratio 与 @supports 对调方向，默认 padding hack，@supports 内升级。
  4. JS-02 / JS-03 / JS-04 / JS-05 / JS-06：套用第 3.1 节的 20 行兜底代码（scrollTop helper + closest polyfill + add/remove + key 归一化 + scrollTo 数值化）。
  5. CSS-03：404 页两个大圆改径向渐变，摆脱 filter 依赖。
  6. CSS-06：约 6 处关键容器补相邻兄弟 margin（gap 保留不动，新旧互不干扰）。
  7. DEP-03：YouTube iframe 加 <noscript> 外链兜底 + 加载失败探测。

收益：IE11 可用度 35% → 约 75%；EdgeHTML 12-14 60% → 约 85%；旧 X5 内核 55% → 约 80%。且不引入任何外部依赖，保住「单文件自包含」的项目特性。

可选 方案 B · 内联 micro-polyfill 约 1 小时 · 与方案 A 的 JS 部分二选一

把 closest / scrollY / classList.toggle 修正 / key 归一化打包成一个约 3KB 的内联脚本，放在两页 IIFE 之前。

不要引入 polyfill.io 之类的公共 CDN

三个理由：① 会引入第三方运行时依赖，摧毁本项目「零外部依赖」的核心优势；② polyfill.io 域名发生过供应链安全事故且已易主，属已知风险源；③ 多一次 RTT，对东南亚移动网络不友好。需要补的东西请一律内联。

不建议 方案 C · 构建期转译（引入 Babel / PostCSS） 投入大 · 收益低 · 有副作用

明确不建议。理由：

  • JS 侧本来就不需要——扫描确认 ES6+ 语法命中 0 处，Babel 无的放矢。
  • CSS 侧解决不了真问题——autoprefixer 能补浏览器前缀（本项目前缀已经写得不错），但补不了 var()、补不了 grid、补不了 IE 私有语法。而 IE11 最大的坑恰恰是 var()。
  • 会摧毁项目优势——引入构建会打破「35KB 单文件、直接丢到任何静态托管就能跑」的现状，而这个特性对一个小团队维护的静态站价值很高。
保底 方案 D · 明确放弃 + 友好提示 15 分钟 · 无论选哪个方案都建议做

如果评估后决定不为 IE11 投入，那至少不要让用户面对一个无法解释的破碎页面。加一段 UA 检测，在老内核顶部显示提示条：把"不知道为什么坏了"变成"我知道这是怎么回事"。

// 放在 <body> 最前，同步执行避免闪烁
if (/MSIE |Trident\//.test(navigator.userAgent)) {
  document.write(
    '<div style="padding:10px 16px;background:#ffb340;color:#1a1d24;' +
    'font:14px/1.5 sans-serif;text-align:center;position:relative;z-index:999">' +
    '当前浏览器版本过旧，部分视觉效果与交互可能不可用。' +
    '建议使用 Chrome / Edge / Firefox 最新版。</div>'
  );
}
// 说明：IE11 的 UA 含 "Trident/7.0"，IE10 及更早含 "MSIE "。
// 若目标是国内 X5 内核，可再补 /QQBrowser|UCBrowser/ 检测并给不同文案。

成本极低，但把最糟的结果——用户困惑地关掉页面——变成了用户理解情况并自行切换浏览器。这一条的性价比高于本报告里的大部分修复项。

8 · 回归与持续保障

兼容性不是一次性工程，改版很容易把已修的项重新踩回去。

  • 复用扫描脚本：.workbuddy/tmp/compat_scan.py（52 条规则）可在每次改版后重跑，比对命中项增量。建议纳入改动清单，或直接挂到 CI 上做 warning 级检查。
  • 本次新发现的既往回归线索：音乐自动播放（既往记录的 P0）在 index.html:775-776 依旧在线，且 preload='auto' 会让 3.1MB mp3 在首屏就拉取——这一点在老内核与东南亚弱网环境下尤其致命（IE11 会完整下载 3.1MB 后才可能播放）。建议顺手改回懒加载。
  • 两条通用规则值得写进约定：① 任何 @supports not 写的兜底都要反问一句"不支持 @supports 的浏览器怎么办"；② 任何 var() 声明都要问一句"这条丢了页面还能读吗"——如果答案是否，就补静态回退值。
  • 版本基线建议（待 UA 数据确认后调整）：核心保障 Chrome 60+ / Safari 12+ / Firefox 78+ / Edge 79+；尽力而为 Chrome 49–59 / Safari 9–11 / Firefox 52–77 / EdgeHTML 15–18 / IE11；明确放弃 IE10 及以下、Opera Mini。
一句话总结

JS 干净得超出预期（零 ES6 语法，无需转译），CSS 的问题看似很多实则收敛到一个根因（var），真正需要立刻动手的只有 4 项。但在动手之前，先花 5 分钟去看一眼 UA 分布——因为你大概率会发现，"老旧内核"在你们的用户群里指的不是 IE。
